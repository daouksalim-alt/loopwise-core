# Six-month maintenance plan

This is a proposed work plan, not a claim of funded work or independent adoption. OpenAI has not confirmed an award. Milestones are targets, not acceptance criteria supplied by OpenAI.

| Period | Work | Evidence to publish |
| --- | --- | --- |
| Month 1 | Support the first three unrelated developers attempting a real integration; record failures as well as successes. | Consented feedback, reproducible issues, actual outcomes. |
| Month 2 | Fix the most consequential observed integration blockers; request retries. | Focused fixes, regression tests and developer confirmation when received. |
| Month 3 | Improve the installation or framework path actually requested by users. | A tested consumer example and updated instructions; clearly label maintainer-created examples. |
| Month 4 | Review keyboard access, labels and error handling with host developers; document remaining limitations. | Reproducible accessibility findings and tested fixes, without an unsupported conformance claim. |
| Month 5 | Investigate repeat use and compatibility across releases. | Versioned regression fixtures and voluntary reports of continued use or abandonment. |
| Month 6 | Review maintenance burden, unresolved issues and whether the library solves a recurring problem. | Public retrospective separating verified integrations, self-reports, tests and outreach. |

## Intended use of Codex

Use Codex to reproduce reported bugs, propose focused patches, build regression tests, check package consumers and keep documentation aligned with behavior. The maintainer reviews changes and validates results before publishing. AI-generated examples and internal test runs are not independent adoption.

## Decision rules

- Prefer an observed user problem over speculative features. If no independent developers try the project, revise the use case and recruitment approach before expanding the API.
- Record an integration only when a developer actually uses the engine in their own project. Label self-reports, relationship to the maintainer and paid testing accurately.
- Ask permission before quoting private feedback or showcasing a project. Do not solicit positive reviews or stars as a condition of support.
- Preserve the MIT license and dependency-free engine. Re-evaluate any new runtime dependency against a demonstrated need.
- Submit an application update only with meaningful new evidence. This plan does not predict an award or commit other developers to participate.
